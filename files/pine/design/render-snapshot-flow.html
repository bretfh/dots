How a :snapshot message flows through the renderer

When a buffer's state changes, its actor notifies subscribers. Each subscriber is a renderer-actor reference. The renderer receives (:snapshot :snapshot <snap>) and decides (a) whether to paint and (b) whether to ask tree-sitter to parse.

The actors involved

Buffer actor

Owns the immutable buffer-state, an undo ring, subscriber list, and the last highlights map.

Receive lambda delegates to hecl.mode:dispatch-message.

— src/buffer.lisp:226–236

Renderer actor (per client)

Holds the client reference. Handles :snapshot, :resize, :switch-buffer, :force-render.

Sits in front of a 60 Hz tick that actually paints.

— src/render.lisp:72–124

Tree-sitter actor

Lives on the server, shared. Receives (:parse :text :language :reply-to), tells the buffer (:highlights :highlights <list>).

— src/render.lisp:51–70

End-to-end trace: user types 'a' in a .lisp file

1(tell buf :insert :text "a") from the dispatch loop. ~ The message lands in the buffer actor's mailbox.
2Buffer actor's receive pulls the buffer's :mode from meta, ~ resolves to :lisp-mode, and calls ~ (dispatch-message lisp-mode self :insert '(:text "a")). ~ Because lisp-mode inherits from text-mode, the ~ text-mode method fires.
3text-mode's method edits sento.actor:*state* (new buffer-state, ~ push old onto undo ring) and calls notify-subscribers.
4notify-subscribers sends (:snapshot :snapshot <snap>) ~ to the renderer actor ref. The snapshot's tick just incremented; ~ its meta carries :mode :lisp-mode.
5Renderer receives :snapshot. This is the block you are reviewing.
6Renderer requests a parse: ~ (:parse :text … :language :commonlisp :reply-to buf) ~ to the ts-actor.
7ts-actor runs compute-highlights and tells the buffer ~ (:highlights :highlights <list>).
8Buffer's :highlights method (on base-mode) stores the hl, then ~ notify-subscribers fires again with a snapshot whose tick is unchanged ~ but whose highlights slot is populated.
9Renderer receives :snapshot again. This is why the tick-guard matters.

The :snapshot handler, annotated

From src/render.lisp lines roughly 86–110:

(:snapshot
 (destructuring-bind (&key snapshot) (rest msg)       ; [1] unpack
   (apply-snapshot snapshot)                          ; [2] update window.snap
   (let ((w (hecl.client:focused-window cli)))        ; [3] need a window
     (when w
       (let* ((name (hecl.buffer:name snapshot))      ; [4] gather deciders
              (tick (hecl.buffer:tick snapshot))
              (rs   (hecl.client:render-state cli))
              (ticks (or (fset:@ rs :parsed-ticks) (fset:empty-map)))
              (last  (or (fset:@ ticks name) -1))
              (mode-name (hecl.buffer:buffer-local snapshot :mode :base-mode))
              (mode      (hecl.mode:find-mode mode-name))
              (lang      (and mode (hecl.mode:ts-language mode))))
         (when (and lang (> tick last))               ; [5] gated parse
           (setf (hecl.client:render-state cli)
                 (fset:with rs :parsed-ticks
                            (fset:with ticks name tick)))
           (let ((buf (find-buffer-for-snap snapshot)))
             (when buf
               (ts-request-parse buf snapshot lang))))))
   (rs-update :dirty t)))                             ; [6] always repaint

What each step does

MarkWhat it doesWhy
[1] Destructure the plist tail :snapshot <v>. All actor messages are keyword-plists.
[2] apply-snapshot finds windows whose window-name matches ~ (hecl.buffer:name snap) and sets their snap slot to this snapshot. That's what the 60 Hz paint tick reads when it draws. — src/render.lisp:142–149
[3] If no focused window exists, nothing needs parsing — skip the gating block. Startup / transient states.
[4] Pull the per-buffer :parsed-ticks from render-state, the last tick we asked ~ ts to parse for this buffer, and the buffer's mode. Everything we need to decide in one let*.
[5] Two gates: lang must be non-nil, and ~ tick > last. If both hold, record the new ~ last-parsed-tick and fire a parse. The mode decides whether tree-sitter applies. The tick-guard prevents the parse loop.
[6] Mark render-state dirty unconditionally. The paint tick reads this flag and repaints. Typing must show up whether or not tree-sitter runs.

The tick gate fixes a spin that the old "null highlights" gate caused

Earlier the gate was (null highlights). Wrong for empty content.

On an empty scratch, compute-highlights returns nil (no captures match). The guard is always true, so every :snapshot triggers another parse → another :highlights nil → another notify → another :snapshot → … two sento workers melt at 250% CPU.

Tick-based gate: we asked for tick N once. If the same tick comes back (from the :highlights reply's own notify), tick == last → skip. Only an edit that advances tick admits a new parse.

The ts-language gate

Step [5]'s other half. Each mode has a ts-language slot. Default nil.

Modets-languageParses?
:base-mode nil no
:text-mode nil no
:lisp-mode :commonlisp yes
:repl-mode nil no
:terminal-mode nil no

Scratch is silent, terminal is silent, lisp files get parsed once per edit. New language = new mode subclass with ts-language :foo + new case in load-language-entry. — src/ts.lisp:264–311

Invariants

  • At most one in-flight parse per (buffer, tick) pair.
  • Buffers whose mode has no ts-language never parse.
  • Repaint is independent of parsing — rs-update :dirty t runs on every :snapshot.
  • Highlights arriving from ts-actor cause one extra :snapshot (tick unchanged) which repaints with new colors but doesn't re-trigger parsing.

Related hotspots

  • ts-request-parse — sends the :parse message; skips silently if the ts-actor doesn't exist. — src/render.lisp:38–46
  • start-ts-actor — only spawns if (ts-loaded-p runtime). Unloaded env = highlight-free, rest works. — src/render.lisp:51–70
  • apply-snapshot — matches by window-name / snap-name. Rename propagation must happen first. — src/render.lisp:142–149
  • render-tick — persistent qsingle-shot that re-arms inside unwind-protect. Immune to body errors. — src/render.lisp:293–333

tl;dr

The handler does three jobs, in order: (a) publish the snapshot to windows for the next paint, (b) decide whether tree-sitter should be asked to re-parse (based on mode's ts-language and an incremented tick), and (c) kick the paint loop unconditionally. Two gates (language, tick) keep the parse path from looping; the dirty flag keeps the paint path unconditional.
